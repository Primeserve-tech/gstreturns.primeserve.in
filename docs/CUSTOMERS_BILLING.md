# Customer accounts and billing — local implementation

This is an additive change to the existing PHP/CodeIgniter GST application, not a replacement portal. Customer mode and paid execution are independently gated and default OFF. No production deployment or real email/API testing has been performed. Do not enable paid execution based only on isolated tests.

## Implementation

`CustomerAccounts` implements normalized unique emails and +91 mobiles, required company/name/password, protected six-digit email OTP (HMAC with the existing encryption secret then password hash), 5-minute expiry, five incorrect attempts, 60-second resend cooldown and three sends/email/hour. Registration IP limits are abuse controls, not duplicate classifications. Old OTPs are invalidated; expired pending payloads are wiped. Successful verification creates an active prepaid account and redirects to Login without signing in.

Offer eligibility, account creation, fixed client prices and one-time promotional ledger credits commit under SQLite BEGIN IMMEDIATE. Offer defaults ACTIVE/₹30; current status is checked at verification completion, not OTP initiation. Database uniqueness covers email, mobile, bonus recipients, billing request IDs, recharge references and ledger credit references. No earlier customer/bonus tables or bonus limiter were found in this checkout; no production customer import has been assumed.

Wallet reservations debit gross charges atomically with return job creation. Postpaid reservations use a separate usage ledger/outstanding balance and approved limit. Prices are integer paise; GST is rounded per unit before multiplying. Each charge snapshots net/tax/gross and supplied state codes. Same-state snapshots allocate CGST/SGST; differing states allocate IGST. Missing state details are marked unallocated, not represented as an issued tax invoice. Usage CSVs are statements, not GST Portal PDFs or tax invoices. Customer and supplier billing details must be verified before invoicing.

User-approved billing units: one accepted return initiation for one return/month; one successful monthly challan, yearly challan or certificate retrieval. Authentication, polling and repeat file downloads do not add charges. Confirmed initiation rejections release reservations; uncertain outcomes remain held for Admin review. A return accepted by the provider is charged even if later processing yields no data: the billable unit is accepted initiation. Document JSON success contracts are still unknown, so such receipts remain under review; original direct PDF/ZIP responses are treated as returned documents. Do not enable production document billing until actual provider success, empty and error contracts have been verified.

Prepaid API key rotation occurs through Admin and is encrypted with the existing server key. Postpaid API keys are encrypted in expiring server-side session records (maximum eight hours), required each login, cleared on logout/reset/expiry, and resolved for subsequent calls. Neither customer key enters new retained API-key audit records. Legacy standalone audit/key behavior remains when customer mode is off. Customer credentials and registration emails are not mirrored into activity logs. Accounting records contain account IDs and amounts, never downloaded GST payloads.

Recharge submissions remain pending until an authenticated Admin independently confirms bank receipt and checks the bank-verification control. Repeated approval credits once; duplicate UTRs are rejected. Top-ups are advances; consumption applies GST once. Postpaid payments reduce outstanding without crediting the prepaid wallet. Unknown upstream outcomes must be reconciled before any new paid retry.

## Zoho configuration

Official references inspected:
- https://www.zoho.com/cpaas/help/api/api-authentication.html
- https://www.zoho.com/cpaas/help/api/email-sending.html
- https://www.zoho.com/cpaas/help/api/multiple-data-centers.html

India endpoint: POST https://cpaas.zoho.in/v1.1/email. Header: Authorization: Zoho-enczapikey <Agent send-mail token>. JSON from.address, from.name, to[].email_address.address/name, subject and htmlbody follow the official API. Only documented HTTP 200 / EM_104 is accepted. This means accepted by Zoho, not confirmed inbox delivery. Raw responses and headers are never logged or returned. No automatic resend of an uncertain email submission. Notifications use escaped Primeserve HTML templates; delivery acceptance/failure metadata contains no OTP or message body.

Configure the names in `.env.customers.example` using the server's secret UI. The actual Agent alias and verified sender address have NOT been supplied/verified. The user-pasted `k=rsa; p=...` is a DKIM PUBLIC record, not a send-mail token. Do not place it in ZOHO_CPAAS_API_KEY. Verify the alias/token/sender association in the Agent SMTP/API page; the send API uses the Agent-specific token rather than an alias URL parameter. Keep DNS/DKIM unchanged. Mark the token secret/masked in Coolify. Keep secret variables runtime-only, not build arguments or frontend variables. No secret value is displayed in Admin.

## Rollback

Stop admissions and workers first; export/reconcile all reserved/review outcomes and pending recharge decisions. Do not reissue upstream calls. Retain the customer accounting database and original encryption key; never discard posted financial records. Revert the application image and flags together only after reviewing whether legacy anonymous access is permitted. Turning off customer mode restores standalone portal behavior and is not an appropriate way to bypass billing. Restore a pre-migration backup only in staging, or under an approved production recovery that also preserves/reconciles subsequent financial entries. Additive tables may remain without affecting legacy paths; do not DROP customer/ledger tables as a rollback shortcut.

### Header balance and wallet reminders
The authenticated GST Services header displays wallet balance for prepaid customers and available credit for postpaid customers, refreshed every 10 seconds while visible. The worker checks prepaid balances once per minute and sends one add-money email per low-balance period. `GST_LOW_BALANCE_PAISE` defaults to `1000` (₹10). Credits have no time-based expiry. Reserved/review amounts are added back for reminder eligibility to avoid treating unfinalized API calls as consumed funds. Above-threshold balance resets eligibility. Delivery failures/uncertain sends are recorded, not automatically repeated. Migration customer-v4 adds only a reminder status table; existing credits and billing history are preserved.

### Admin navigation and reports
`/admin/customers` now groups controls under Home, Customers, Payments, Pricing, Reports, and Settings; API Activity retains its existing separate screen. Payment approval uses an explicit decision dropdown and preserves independent bank verification. Reports provide .xlsx exports with inclusive IST From/To dates and an optional customer filter: customer registration details, prepaid/postpaid payments, API usage and tax breakdowns, wallet transactions, and bonuses. Export columns are explicitly allowlisted and omit credentials. Date-range exports are not limited to the 500-row dashboard preview; over 100,000 records prompts a narrower date range. Existing monthly CSV routes remain compatible.
